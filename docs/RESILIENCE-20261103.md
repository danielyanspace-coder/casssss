# Устойчивость к нагрузке: 3 ноября 2026

Проверена актуальная рабочая версия /srv/luckybox. SQLite уже использует WAL,
а денежные изменения идут через транзакции, дедупликацию платежей и журнал
ledger с триггерами. Сам факт параллельных обращений не означает потерю денег.

## Изменения

- До разбора JSON ограничивается количество открытых API-запросов: обычные
  128, callbacks 32, SSE 256, загрузки чеков 4. Корзины независимы.
  При заполнении возвращается 503 + Retry-After, очереди без предела нет.
  Callback кошелька не ограничивается по частоте/IP; ограничено одновременно
  выполняемое HTTP-обслуживание. Отказ происходит до запуска обработчика.
- JSON обычного запроса ограничен 1 MiB, чеков — 8 MiB. Ограничен и размер
  карт памяти rate limiter: по 10 000 ключей; активные записи не вытесняются.
- Проверки scrypt: не более 4 одновременно; очередь сверх лимита не создаётся.
- Денежные транзакции BEGIN IMMEDIATE резервируют запись до чтения баланса.
  SQLite synchronous=FULL сохраняет подтверждённые транзакции при отключении
  питания при условии корректного fsync на хранилище. busy_timeout=250ms
  ограничивает блокировку event loop сторонним писателем. Глобальный обработчик
  возвращает 503 на SQLITE_BUSY/LOCKED; отдельные обработчики с собственным
  catch могут по-прежнему возвращать прикладную ошибку.
- Фоновая сверка Sicilia планирует следующий запуск после завершения текущего;
  оплаченная история не загружается целиком в Set при каждой сверке.
  Индекс paid_at поддерживает выборку новых оплат. Уведомление на границе
  времени может повториться; это только SSE, денежная дедупликация сохранена.
- Запросы рассылки имеют timeout 20 секунд. Медленные SSE-клиенты закрываются
  при backpressure, чтобы буфер ответов не рос без предела.
- SIGTERM прекращает приём запросов, закрывает SSE и ждёт завершения HTTP
  до 90 секунд. Затем база закрывается. systemd ждёт до 100 секунд.
  При превышении срока процесс завершается с ошибкой; внешние операции с
  неопределённым результатом требуют существующей сверки по ID ордера.
- HTTP: получение тела до 30 секунд, заголовков до 15 секунд, keepalive 5 секунд.

Настройки: HTTP_CONCURRENCY, CALLBACK_CONCURRENCY, STREAM_CONCURRENCY,
PASSWORD_CONCURRENCY. Значения по умолчанию — начальная конфигурация, не SLA.
Увеличивать только после измерений памяти, задержек и SQLITE_BUSY.

## Проверка

На изолированной базе, без ключей провайдеров, 2000 запросов, 64 клиента,
400 открытий кейсов и 1600 чтений игрока. Все HTTP 200; integrity_check=ok;
суммы ledger совпали с обоими балансами. Рабочая версия: 14.33 s, 140 req/s,
p95=552ms. Вариант на основной ветке: 12.93 s, 155 req/s, p95=494ms.
Это короткий локальный прогон, без задержек реальных провайдеров и интернета.

Отдельно проверены 503 при переполнении, независимый резерв callback,
восстановление слотов, предел KDF, отсутствие наложения фоновых задач,
реальный SIGTERM посреди получения тела HTTP-запроса (ответ 200, выход 0).

Пройдены: auth 87, casino 110, Sicilia 156, crypto 46, wager 36,
broadcast 15, ratelimit 13, reserve-gateway.
Общий API-тест: 425 успешных проверок, две ошибки также на исходной версии:
устаревшее ожидание HTML /admin и константы RTP 70% в тесте апгрейда.
Тест payout-check также не зелёный на исходном коде: тестовый игрок не
погасил долг отыгрыша. Эти проверки не отключены, результаты не скрыты.

Воспроизведение: npm run test:resilience. Все деньги тестовые; рабочая база
не используется. test/load-resilience.mjs запускать только на одноразовой
DEV_MODE-базе без провайдерских ключей.

## Границы отказоустойчивости

Сейчас один сервер, один HTTP-процесс, один SQLite-файл на локальном диске.
Поломка машины/диска/сети останавливает сайт. Эти изменения ограничивают
перегрузку и улучшают восстановление, но не дают multi-host HA.
Не запускать кластер Node на общей базе в надежде получить линейный прирост:
синхронный SQLite и тяжёлые игровые вычисления ограничивают общий поток.
Для HA требуется отдельный проект: PostgreSQL с резервной репликой,
внешние sessions/лимитеры/события, два экземпляра приложения, балансировщик,
миграция денежных транзакций и повторный тест отказов/согласованности.

Таймер резервного копирования и watchdog включены; локальные копии есть.
Копии на той же машине не защищают от её потери. Ключ PAYOUT_DATA_KEY нужен
для восстановления карт и должен храниться отдельно от базы. Перед выкладкой
создан согласованный снимок SQLite и проверен integrity_check.
Источники: https://www.sqlite.org/pragma.html#pragma_synchronous и
https://nodejs.org/api/http.html#serverclosecallback .
