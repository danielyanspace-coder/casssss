# Развёртывание LuckyBox

Здесь лежит всё, что нужно, чтобы поднять проект на своём сервере: службы,
конфиг nginx, резервное копирование и два скрипта.

## Что в папке

| Файл | Зачем |
|---|---|
| `install.sh` | Первичная установка на чистый Ubuntu/Debian, одной командой |
| `update.sh` | Выкат новой версии: копия базы, свежий код, перезапуск |
| `nginx.conf` | Обратный прокси, HTTPS, заголовки, **обязательный блок под SSE** |
| `luckybox.service` | Служба веб-сервера |
| `luckybox-bot.service` | Служба бота, отдельным процессом |
| `backup.mjs` | Согласованная копия базы с проверкой целостности и ротацией |
| `luckybox-backup.service` + `.timer` | Копия раз в час |

## Какой сервер нужен

**VPS/VDS с полным доступом (KVM), не shared-хостинг.** Приложению нужны свои
процессы, systemd, nginx и порт - на общем хостинге ничего этого нет.

| | Минимум | С запасом |
|---|---|---|
| Ядра | 1 | 2 |
| Память | 2 ГБ | 4 ГБ |
| Диск | 40 ГБ SSD | 80 ГБ SSD |
| Система | Ubuntu 22.04 | Ubuntu 24.04 |

Откуда числа. Код с обложками занимает 8,5 МБ, зависимости - 40 МБ, база на
старте меньше мегабайта. Диск съедают не они, а резервные копии: их четырнадцать
штук, каждая - полный файл базы, и с ростом истории раундов это главная статья.
Память: приложение и бот в работе держат около 200 МБ на двоих, но сборка
`better-sqlite3` при установке разово требует почти гигабайт - на 1 ГБ без
подкачки она падает.

## Установка

Нужен сервер с Ubuntu 22.04+ и домен, у которого A-запись указывает на его
адрес. Домен должен указывать на сервер **до** запуска: сертификат выпускается
проверкой через этот домен.

```bash
git clone <репозиторий> luckybox && cd luckybox
sudo bash deploy/install.sh ваш-домен.ru
```

Скрипт заведёт пользователя, положит проект в `/srv/luckybox`, поставит Node,
зависимости, службы, nginx и сертификат. `.env` он создаст из образца и
сгенерирует `PAYOUT_DATA_KEY`, но токен бота и ID администраторов вы вписываете
руками: подставлять их скриптом - верный способ однажды закоммитить их.

Дальше:

```bash
sudo nano /srv/luckybox/.env        # TELEGRAM_TOKEN, ADMIN_TG_IDS, BEELINE_PHONE
sudo systemctl start luckybox luckybox-bot
curl -sf https://ваш-домен.ru/api/config > /dev/null && echo "сервер отвечает"
```

Бот сам поставит кнопку меню, ведущую в мини-апп.

## Выкат новой версии

```bash
sudo bash /srv/luckybox/deploy/update.sh
```

Сначала снимается копия базы, потом подтягивается код, потом проверяется
математика кейсов - и только затем перезапуск. Если решатель вероятностей не
сойдётся, вы узнаете об этом, пока старая версия ещё работает.

## Резервные копии

Копия снимается **не** копированием файла. База в режиме WAL: часть свежих
записей лежит в `app.db-wal`, и `cp` во время работы даёт снимок из разных
моментов. `backup.mjs` использует встроенный механизм SQLite - согласованный
снимок без остановки сервера, - потом проверяет целостность и сворачивает
журнал, чтобы копия была одним самодостаточным файлом.

```bash
sudo systemctl start luckybox-backup     # прогнать сейчас
systemctl list-timers luckybox-backup    # когда следующая
ls -la /srv/luckybox/data/backups
```

**Копия рядом с базой спасает от испорченной записи и ошибочного удаления, но
не от потери сервера.** Настоящая копия - та, что уехала на другую машину.
Настройте `RCLONE_REMOTE` в `.env`, и скрипт будет отправлять её туда.

Копии сжимаются: база состоит из повторяющихся строк истории и жмётся
примерно в семь раз. При живом потоке это решает - один раунд весит около
230 байт, три сотни игроков за сутки дают четверть гигабайта, а копий мы
держим четырнадцать.

Восстановление:

```bash
sudo systemctl stop luckybox luckybox-bot
cd /srv/luckybox/data
sudo -u luckybox gunzip -c backups/app-….db.gz > app.db
sudo rm -f app.db-wal app.db-shm
sudo systemctl start luckybox luckybox-bot
```

### Про ключ выплат

`PAYOUT_DATA_KEY` лежит в `.env`, а не в базе. Номера карт зашифрованы им, и
копия базы без ключа их не вернёт **никогда**. Храните ключ отдельно от базы и
отдельно от её копий. Менять его после появления первых заявок по карте нельзя.

## Почему в nginx отдельный блок под `/api/payments/events`

Это Server-Sent Events - ответ, который никогда не заканчивается. nginx по
умолчанию копит ответ в буфере и отдаёт целиком, а значит не отдаст никогда:
игрок оплатит и не увидит зачисления, пока не перезагрузит страницу. Плюс
обычный таймаут в 60 секунд рвал бы поток каждую минуту. Блок с
`proxy_buffering off` и часовым таймаутом обязателен.

## Проверка после установки

```bash
systemctl status luckybox luckybox-bot
journalctl -u luckybox -f
systemctl list-timers luckybox-backup

# ограничитель частоты жив
for i in $(seq 1 12); do curl -s -o /dev/null -w "%{http_code} " \
  -X POST https://ваш-домен.ru/api/promo/redeem \
  -H 'Content-Type: application/json' -d '{"code":"НЕТ"}'; done; echo
# ожидается: несколько 401/400, дальше 429
```

## Чего здесь нет

- **Авторизации через Telegram на домене.** Сейчас вход только через мини-апп:
  сервер принимает подписанный `initData`. Виджет Telegram Login использует
  другую схему подписи и требует сессии - это отдельная задача, не настройка.
- **Мониторинга и оповещений.** Ни одно падение никуда не напишет.
- **Второго сервера.** Всё на одной машине, включая базу.
